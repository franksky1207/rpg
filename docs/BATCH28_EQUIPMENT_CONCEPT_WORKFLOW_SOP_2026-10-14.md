# 《文明戰線》第28批｜裝備概念圖製作與入庫標準流程 v2.0

更新：2026-10-14。適用：銀河 G001～G100、宇宙 U001～U100、高維 H01～H10。**最新 GitHub main 是唯一正式資料來源。** 本 SOP 以 2026-10-11 原始製圖規則及前20套實際兩圖結構為基礎重寫，取代本文件舊版；不以逐次附加補丁方式維護。

## 1. 作業原則與分工

- **製作單位是一套裝備，不是一整批圖片。** 每套獨立製作兩張圖，完成一套再進下一套。五套是一次工作批量，不是一張畫布的內容，也不是一次生圖指令。
- **一般 ChatGPT／影像工具**：查明正式名稱與美術規格，依序產生各套的兩張獨立圖。使用者授權一批五套時，可連續完成，無須每張停下要求下一步指令。
- **ChatGPT Work**：接收十張原始圖片或 ZIP，檢查與入庫、更新資料、執行必要驗證、提交 GitHub main、核對 Actions；不得自行把多張合成或重生。
- **使用者**：美術審核與批准。圖已生成、入庫、CI 全綠，都不等於批准。
- 若工具限制使十個獨立檔案無法產出，應明確回報未完成的套裝／圖片；不得將一張拼貼圖裁切冒充十張，也不得聲稱已完成 ZIP 或入庫。

## 2. 每批開始前核對正式資料

先讀取最新 main：
1. `PROJECT_HANDOFF.md` 與本 SOP。
2. `development/3d-source/equipment/concepts/_concept-index.json`、相關 identities／owner 與指定五套 `concept-notes.md`。
3. `docs/3D_EQUIPMENT_CONCEPT_BATCH_ART_WORKFLOW_2026-10-11.md`、`docs/3D_EQUIPMENT_ALL_EPOCH_FIVE_SLOT_CONTRACT_2026-10-13.md` 及美術方向。
4. 參考相鄰已製作套裝的輪廓、材質與區域演進，避免僅換色；正式 ID、sourceKey、區域／Boss、五槽名稱必須逐套核對，不可從 slug 猜測。

編號：銀河 G001～G100；宇宙 U001～U100；高維 **H01～H10**，不可寫成 H001～H010。

## 3. 逐套、逐張製作（最重要的執行順序）

每套必須完成下列兩個**彼此獨立的影像產物**，再開始下一套：

**第一張：`overview-front-side-back.webp`**
- 只呈現當前同一套裝備的完整穿戴角色，正面、側面、背面三視圖；比例、材質、配件相互一致，頭盔完整遮蔽可辨識五官。
- 正側背排在這一張圖內是正確的；不得混入下一套裝備或五槽拆件大表。

**第二張：`equipment-five-slots.webp`**
- 只呈現當前同一套的五槽獨立裝備：武器、頭盔、鎧甲、鞋子（左右成對）、飾品。
- 裝備分件、厚度、握柄、背部掛座及穿卸所有權要清楚；不得將飾品重複畫成鎧甲永久部分、把鞋與甲的硬殼重複歸屬。
- 五槽可排在同一張拆件圖內；不得與總覽圖合併。

**執行次序範例**：G026總覽 → G026拆件 → G027總覽 → G027拆件 → G028總覽 → G028拆件 → G029總覽 → G029拆件 → G030總覽 → G030拆件。**每一步產生一個獨立圖片檔**；若影像工具支援單次多檔輸出，必須逐一確認每個輸出仍是獨立圖片，不能把整批內容交給單一畫布。

每張完成就保留原始產物；可在對話顯示。**「一次完成」僅指工作連續進行，不指一次產生一張含十格的大圖。** 不使用十宮格、跨套拼貼、contact sheet 或從同一張合成圖裁切成多個檔案充數。

## 4. 圖片交付與入庫

1. 每批五套，共**十個真正獨立的 WebP**；每套正式目錄內各有上述兩個檔案。圖片以可讀品質為優先，參照原 SOP 的尺寸與壓縮建議；保留可追溯來源，不能虛構原稿或雜湊。
2. 製作端完成後，盡可能將十張依套裝目錄整理成單一 ZIP，交付 Work。跨對話需要使用者附加 ZIP；工具無法打包時如實交付可用圖片及缺項。
3. Work 先檢查 ZIP 檔案數、格式、尺寸、bytes、SHA-256，並**逐張確認圖片內容確屬指定套裝及指定類型**；若只有一張拼貼、缺圖、跨套、總覽／拆件混合，應停止該批入庫並回報，不以裁切修補。
4. 核對標準路徑 `development/3d-source/equipment/concepts/<epoch>/<stable-id>-<slug>/`。不覆寫已批准圖；既有待審圖若要更換，須保存原版本及差異證據。
5. 使用 `python3 scripts/equipment-concepts.py generate`、`python3 scripts/equipment-concepts.py validate`、`python3 -m unittest discover -s tests/equipment-concepts -v`；重跑 generate 應零差異。索引衍生欄位由正式腳本維護，人工 notes 不得被覆蓋。
6. 新圖維持 `conceptApproved=false`、未建模；既有已批准狀態不可被批次覆寫。開發圖、原稿與 .blend 不得進正式 Pages 或 Service Worker 預載，依修改範圍執行 `node scripts/publish-asset-audit.cjs`。

## 5. 提交前檢查與 GitHub Actions

- **必要檢查優先**：依實際修改範圍檢查裝備索引、檔名／圖像、來源映射、發布隔離與受影響契約；不強制建立共用預檢入口，不要求每批執行全部無關測試。
- **避免重演本次 CI 失敗**：若改 JS 引用或來源驗證器，核對正式快取版本與 `development/hybrid-comparison/t2b3-v1/source-version.cjs` 的來源版本鎖；若改受清冊追蹤檔案，連帶重新計算 `development/hybrid-comparison/t2b3-v1/inventory.json` 的 SHA-256、bytes 與 totalBytes。保留歷史 source 鎖，不得為求綠燈停用 workflow 或放寬驗證。
- 原則上整批整合為一個 main commit；提交前檢視差異，禁止夾帶正式戰鬥、存檔、GM、背景／極簡、音訊、2.5D 或發布開關等無關修改。
- 提交後查核**最新 commit exact HEAD** 應觸發的 Actions；分別回報成功、失敗、執行中、未觸發。Runtime Integrity 有 paths 觸發限制，未觸發不等於通過。
- 失敗時讀取 job log，修復本次範圍內根因與連帶清冊／版本問題，再驗證；不得偽造全綠。

## 6. 批次驗收與固定回報

每批結束回報：
1. **修改內容**：五套正式名稱、各兩張圖、實際新增／更新檔案與索引／notes。
2. **自我檢查**：十個獨立圖片內容、尺寸／雜湊、五槽身份、腳本／契約／發布隔離及未執行項目。
3. **實機驗收清單**：本批可由使用者實際檢視的五套總覽與拆件，以及需後續審核的美術問題；不冒稱已批准。
4. **提交與待補**：main commit SHA、exact-HEAD Actions 狀態、限制與待補事項。
