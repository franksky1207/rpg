# 《文明戰線》快速施工與自動驗收 SOP（2026-10-23）

## 適用範圍
最新 `main` 為唯一來源。每批原則一個工作分支、一個 PR。每批需先界定「必須改、不能改、相關測試、發布條件、人工真機保留項」。

## 一次委派的五個階段
1. **變更前盤點**：找出全部擁有者、正式入口、歷史完整性鎖、HTML 快取引用、相關 Browser 測試。不可只看第一個失敗案例。
2. **同一 PR 一次整合**：程式、精確測試斷言、必要 HTML cache bust、文件一起處理；禁止為了綠燈刪除測試、單純放寬 timeout 或關閉保護器。
3. **分層驗收**：本機語法及快取預檢 → 快速 PR Preflight → 相關功能 Browser → 完整 Runtime（受影響時）→ Pages 發布前驗證。PR 中先達標，才合併。
4. **失敗診斷迴圈**：從第一個失敗步驟抓日誌，分類為正式功能、測試契約、時序競態、資源快取、CI 基礎設施；掃描相同根因的其他測試，再在原 PR 補修。每次修復附上根因及新舊行為證據。若超出批次範圍或反覆失敗，停止合併並回報，不可假稱完成。
5. **發布封箱**：審查 PR head 的必要成功；合併最新 main；同 SHA 核對 Runtime、正式戰鬥、Pages、相關回歸 Actions。無失敗、無 pending 才能標記 CI 封箱，人工 iPhone 實機項目明列「未驗證」。

## 自動化分工
- `.github/workflows/fast-development-preflight.yml`：PR 的輕量變更影響與 JS/CSS 快取版本預檢；報告受影響領域及舊版鎖注意事項，快速失敗則阻止把問題延後到 Runtime。
- `scripts/dev-fast-preflight.cjs`：亦可在本機用 `node scripts/dev-fast-preflight.cjs <base-ref>` 執行，只讀檢查，不更動正式遊戲檔案。
- 既有 `Runtime Integrity`：符合其 PR 路徑時完整執行；不能把僅有 PR 其他十項綠燈稱為 Runtime 通過。
- 既有正式 Pages：維持 main push 的真實發布機制。快速關卡不是 Pages 發布的替代證據。

## 每批固定回報
`範圍 / PR / PR head SHA / 受影響測試 / 成功與失敗 / 正式 main SHA / 同 SHA Runtime & Pages / 真機限制 / 是否封箱`。

## 不要重複過去第19-3批錯誤
- 修改 JS/CSS 時一起同步 `index.html` 版本，且檢查歷史 exact-blob baseline 是否須精確授權。
- 不能把「動畫舞台絕對置中」與「動畫＋雙方 HP＋停止鈕整體可見」混為一談；應統一驗收契約後掃描全部測試。
- 禁止為等待結果重複建立補修 PR；應持續更新原 PR 至證據齊全。
- 避免用極端瞬殺數值測試短暫 HUD；必要時測試真實戰鬥結算與畫面可見性分開驗收。
- 若 GitHub Actions 正在跑，不能宣稱完成；可一次完成本次可執行的施工，最終結論仍依已返回證據。
