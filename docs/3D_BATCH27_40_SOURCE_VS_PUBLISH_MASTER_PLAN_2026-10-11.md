## C. 資源策略與容量預算（新建議，尚非既定測量值）

1. 基線為 **27.57 MB** 的 360 檔。第 27～40 批每次提交記錄：原始工作樹 MB、發布 artifact MB、各紀元 GLB/紋理/動畫 MB、首次下載量、各場景獨立下載量、媒體 Cache Storage 使用量，以及版本間增減。不能用打包容量冒充真實網路流量。
2. 建議以 **Pages 目標 < 500 MB、預警 600 MB、硬性檢討 700 MB** 當作本專案**內部規劃門檻**；不是 GitHub 官方配額的聲明，也不是允許每次進入遊戲一次下載 500 MB。實際 GitHub Pages/Actions 最新限制須於大量素材進駐前再查核。
3. 手機依「**首屏小、進入才載、離開可釋放、再進可重用**」實作。首屏只抓當前紀元需要的共用骨架／近景／最小必要貼圖；切地圖、裝備、敵人、Boss 再載特定 bundle；預載不應一次下載全部 1,000 個異宇宙深度場景。
4. 共用材質、動畫及骨架的複用優先；重要 Boss 外觀可更豪華、具獨特輪廓／動作／特效。每批實測 **GPU memory 代理指標、三角面數、骨架數、貼圖尺寸、shader compile、首次/熱載、FPS 及場景釋放**，不單看檔案 MB；按低/中/高畫質提供合理層級，至少可退至 2D/文字。
5. 發布程式必須隨 3D 新資產擴充：`scripts/publish-assets.cjs` 的依賴、manifest、動態路徑與授權政策；`scripts/build-publish-dry-run.cjs`、`.github/workflows/publish-optimized-pages.yml`、Stage 4 Gate、Browser tests。**不得依賴「未知的動態路徑」會被現有字串掃描自動發現**；第 27 批先新增顯式資產台帳／閉包驗證，再逐批增量。
6. WebP／KTX2／mesh compression／LOD 要依設備功能和實測選擇；不能只產出有壓縮標記、實際瀏覽器卻解不開的 GLB。CDN 禁止依賴改回本地化；授權文件、Babylon.js 版本與 decoder 的實際必要檔都應納入。
7. 音樂與媒體 Cache Storage 保持 SHA 指紋、206 Range、使用量與清除行為；遊戲資料/本機存檔/帳號/GM 權限不得跟媒體快取一起清除。頻繁更新期 JS/CSS **不提早引入永久 cache-first**；待第 40 批及後續穩定再獨立規劃程式資產原子快取。
8. **GitHub Pages 既已切換 Actions 發布**：任何 main 更新都要以最新 exact-HEAD Actions 建置及瀏覽器測試為準。部署失敗時不能宣稱站點成功更新；保留前次成功發佈 SHA 和可回退資產與 settings 記錄。

## E. 每批交付與測試中心

- 本批新增可視內容（新裝備、Boss、動畫、場景、特殊環境/戰鬥）**加入既有 GM 3D 測試中心合適分類/場景選項**，現行八分類與 31 案例為基線，不為每隻怪物新增重複入口；以分類/篩選/名稱選單選取。測試中心保留「正式角色外觀快照／自由展示」兩模式及唯讀隔離，禁止修改正式 save。
- 正式 UI 視覺優先：不是僅 GM 中好看。每個功能均要在正式頁面真的有立體空間、動畫、回饋、必要標示/按鈕；**文字與 3D 並用**，清楚能看懂裝備名、能力、速度、操作。
- **每批固定提交物**：當批 source 原始檔清單／sha／授權、發布成品清單／sha／大小、正式身份映射、變更的玩家 UI／GM 選項、測試及容量差異、GitHub exact-HEAD CI 狀態、手機／桌機實測項目、commit SHA／待補。即使 source 很大、網站仍能小，不得漏記變更。
